## ⚠️ Изменения от 24.11.2026 (решения проекта)

1. **Боевой API СМП/НМП нам не передают.** Доступ к нему и интеграцию будут делать другие люди — это вне нашей зоны ответственности. Всё, что в ТЗ написано про «реальный API заказчика», для нас означает «контракт, который мы задаём сами».
2. **API делаем свою заглушку:** `mock_api.py` — отдельный Flask-сервер на порту 5001. Он отвечает по HTTP и ведёт себя как настоящий: коды ответов, задержки (по желанию), ошибки.
3. **Данные храним в своих SQL-таблицах:** SQLite, файл `data.db`, схема в `schema.sql`, примеры в `seed.py`. Таблицы нужны только для примеров работы и демонстрации — реальных пациентов там нет.
4. **Обмен всё равно идёт по HTTP через `requests`.** Приложение не должно знать, что API — заглушка: никаких `if USE_MOCK` в роутах. Когда появится боевой API, меняются только `api_client.py` и `.env`, а шаблоны и `app.py` — нет.
5. **Контракт фиксируем мы:** URL, имена полей, коды ответов описаны в разделе 2.12 и реализованы в `mock_api.py`. Это и есть «документация API» из ТЗ — только наша.

# Часть 1. Исходное ТЗ (дословно)

> Текст ниже — как его отдал заказчик. Сохранён для истории. Пункты про реальный API, интеграцию и этап 3 заменены решениями из блока выше и разбором в Части 2.

## 1.1. Задача

Разработать программное обеспечение для взаимодействия со станцией скорой/неотложной медицинской помощи (СМП и НМП).

## 1.2. Функциональные требования

Приложение должно позволять сотруднику станции/бригады СМП (конкретная роль уточняется):

1. Просматривать список полученных вызовов.
2. Просматривать информацию о вызове.
3. Просматривать информацию о пациенте.
4. Добавлять случай медицинского обслуживания.
5. Добавлять «Дневники».
6. Записывать пациента на приём к врачу.
7. Переходить на портал врача.

## 1.3. Технические требования

1. Реализовать адаптивную вёрстку — приложение будет использоваться на планшетах с разными разрешениями экрана.
2. Backend реализовать на Python 3 с использованием Flask.
3. Обеспечить интеграцию с API СМП/НМП.
4. Адрес API и параметры подключения вынести в конфигурацию/переменные окружения, не хардкодить.
5. Предусмотреть логирование ключевых операций и ошибок интеграции с API.
6. При ошибках API приложение не должно падать: пользователь видит понятное сообщение и продолжает работу.
7. ПО должно запускаться на отечественных ОС (в рамках разработки ориентируемся на Debian — крупнейшие отечественные дистрибутивы базируются на нём, Python-стек легко переносится).

> ⚠️ **Наша поправка к п. 3:** «интеграция с API СМП/НМП» = работа с нашим `mock_api.py` по зафиксированному контракту. Боевой API появится не у нас и не в этом проекте.

## 1.4. Ожидаемый результат

1. Исходный код приложения.
2. Инструкция по запуску и настройке.

## 1.5. Экраны и навигация

Общие элементы (`base.html`):

# Часть 2. Разбор по пунктам

## 2.0. Что это вообще за приложение (одним абзацем)

Тонкая веб-обёртка над чужим API. Своей базы данных нет. Планшет в браузере → наш Flask → (VPN) → API больницы → JSON обратно → Flask рендерит HTML. Из CRUD нужны только **Read** (вызовы, пациенты) и **Create** (случай, дневник, запись к врачу). Update/Delete в ТЗ нет — не тратим на них время.

Три следствия, которые определяют всю архитектуру:

1. **Мы не храним данные пациентов.** Боевой базы у нас нет. Но для примеров и демонстрации делаем **свою** SQLite-базу `data.db` за заглушкой `mock_api.py` — она живёт только на машине разработчика/демо-стенде и в Git не попадает.
2. **Формат JSON задаём мы сами** — он описан в разделе 2.12 и реализован в `mock_api.py`. Все поля всё равно проходят через один адаптер (`api_client.py`), чтобы при появлении боевого API поменять только его.
3. **Связь нестабильна по определению** (VPN + планшет; на демо — забытый запуск мока) → обработка ошибок не «доп. фича», а часть основного сценария.

## 2.1. Функциональные требования — 7 пунктов

### Ф1. Просмотр списка полученных вызовов
**Что реально надо:** страница `/`, таблица или карточки: номер вызова, адрес, ФИО, статус. Кнопка обновления и переход в карточку.
**Как:** `GET {API_BASE_URL}/api/calls` → список словарей → нормализация → `index.html`.
**Грабли:** API может отдавать постранично (`page`, `limit`) или с конвертом `{"data": [...], "total": N}`. Если список пуст — показывать «Вызовов нет», а не пустой экран и не `TypeError`.
**Готово, когда:** при живом mock_api список виден, при выключенном — красный баннер, страница жива.

### Ф2. Просмотр информации о вызове
**Что реально надо:** `/call/<id>`: номер, адрес, повод, статус + краткие данные пациента, кнопки на формы.
**Как:** `GET {API_BASE_URL}/api/calls/<id>` → нормализация → `call_detail.html`.
**Грабли:** 404 по несуществующему id — это не падение, а «Вызов не найден» + ссылка назад. id приходит из URL строкой: не сравнивать `"5"` и `5`.
**Готово, когда:** открывается и существующий, и несуществующий id без Traceback.

### Ф3. Просмотр информации о пациенте
**Что реально надо:** `/patient/<patient_id>`: ФИО, дата рождения, полис ОМС, медданные.
**Как:** `GET {API_BASE_URL}/api/patients/<patient_id>`.
**Грабли:** даты приходят в разных форматах (`2020-01-31`, `31.01.2020`, timestamp) — приводить к одному виду в адаптере, а не в шаблоне. Полис — строка, ведущие нули не терять (не превращать в число).
**Готово, когда:** поля отображаются, пустые значения показываются как «—», а не `None`.

### Ф4. Добавление случая медицинского обслуживания
**Что реально надо:** форма `/call/<id>/case/new` → `POST` → возврат на карточку вызова с зелёным уведомлением.
**Как:** `POST {API_BASE_URL}/api/calls/<id>/cases` с JSON тела.
**Грабли:** API может отвечать 201 без тела или 200 с `{"id": ...}` — обрабатываем оба. Обязательные поля валидируем ДО отправки (пустая форма → сообщение, а не 400 от сервера).
**Готово, когда:** запись создаётся в mock, пользователь возвращается на карточку, при ошибке — красное сообщение и данные формы не потеряны.

### Ф5. Добавление «Дневников»
**Что реально надо:** форма `/call/<id>/diary/new` → `POST`.
**Как:** `POST {API_BASE_URL}/api/calls/<id>/diaries`.
**Грабли:** «Дневник» — это текстовая запись с датой/временем; серверное время и клиентское могут расходиться. Если API требует дату — брать её из ответа сервера, а не с планшета.
**Готово, когда:** дневник создаётся и виден после обновления карточки (если API отдаёт дневники в составе вызова).

### Ф6. Запись пациента на приём к врачу
**Что реально надо:** форма `/patient/<patient_id>/appointment/new` → `POST`.
**Как:** `POST {API_BASE_URL}/api/patients/<patient_id>/appointments`.
**Грабли:** слотов/врачей в нашем контракте нет — врач и дата вводятся вручную (решение 2.10, п. 8). Если появится боевой API со слотами, добавится отдельный `GET` и выпадающий список.
**Готово, когда:** запись создаётся, пользователь возвращается на карточку пациента.

### Ф7. Переход на портал врача
**Что реально надо:** кнопка в шапке, открывает внешний URL в новой вкладке.
**Как:** `DOCTOR_PORTAL_URL` из `.env` → `href` с `target="_blank" rel="noopener"`.
**Грабли:** если переменная не задана — кнопку скрывать или писать «не настроено», а не вести на `None`. Никакого хардкода адреса.
**Готово, когда:** ссылка меняется правкой `.env` без правки кода.

### Сводная таблица по функционалу

| № | Экран | URL | Метод API (предполагаемый) | Ключевой риск |
|---|-------|-----|----------------------------|----------------|
| 1 | Список вызовов | `/` | `GET /api/calls` | формат ответа, пустой список |

## 2.2. Технические требования — 7 пунктов

### Т1. Адаптивная вёрстка под планшеты
**Что значит:** вёрстка живёт на 1024×768, 1280×800, 1920×1200 и в обеих ориентациях, без горизонтального скролла и «уехавших» кнопок.
**Как:** `<meta name="viewport" content="width=device-width, initial-scale=1">`, Bootstrap-сетка (`col-md-*`, `col-lg-*`), крупные тап-зоны (≥44 px), `table-responsive` для таблиц, `sticky` шапка.
**Как проверить:** F12 → Device Toolbar → iPad / 1024×768 / повернуть; плюс реальный планшет в конце.
**Грабли:** фиксированные `width: 1200px`, мелкий шрифт, hover-меню (на планшете нет hover).

### Т2. Backend на Python 3 + Flask
**Что значит:** серверная логика только на Flask, без Django/FastAPI «для удобства».
**Как:** `app.py` с роутами, `render_template`, `flash`, `redirect`. Версия Python — 3.10+ (Debian 12 даёт 3.11).
**Грабли:** не тащить `async`, не смешивать с фронтенд-фреймворками; Jinja2 уже внутри Flask.

### Т3. Интеграция с API СМП/НМП
**Что значит у нас:** приложение получает и отправляет данные только через HTTP к `mock_api.py`. Локальных «придуманных» списков в коде нет — всё берётся из SQLite **через заглушку**, а не читается напрямую из файла БД.

**Как:** один модуль `api_client.py`: функции `get_calls()`, `get_call(id)`, `get_patient(id)`, `create_case(...)`, `create_diary(...)`, `create_appointment(...)`. Внутри — `requests` с `timeout`, заголовками, базовым URL из `.env`.

**Почему так, а не «просто SQLite в app.py»:** прямой доступ к БД пришлось бы переписывать при появлении боевого API. Слой заглушки сохраняет архитектуру «клиент → HTTP → сервер» и даёт возможность показать обработку ошибок (остановил мок = API упало).

**Грабли:** самодельная сборка URL (`base + "/" + path` даёт двойные слэши), отсутствие `timeout` (запрос висит вечно и вешает Gunicorn-воркер), игнорирование кодировки ответа, чтение SQLite из двух процессов без `check_same_thread=False`/отдельного соединения на запрос.

### Т4. Конфигурация через `.env`, без хардкода
**Что значит:** ни адреса API, ни пути к БД, ни URL портала в коде нет.
**Как:** `config.py` + `python-dotenv`, переменные:
`FLASK_SECRET_KEY`, `API_BASE_URL` (по умолчанию `http://127.0.0.1:5001`), `API_TIMEOUT`, `DB_PATH` (`data.db`), `DOCTOR_PORTAL_URL`, `LOG_LEVEL`. `API_TOKEN` добавляем сразу в `.env.example`, но используем только если появится боевой API.
Плюс `.env.example` с теми же ключами и примерными значениями.
**Грабли:** `.env` в `.gitignore`; `os.environ["X"]` падает при отсутствии переменной — лучше `os.getenv("X", default)` + явная проверка на старте с понятным сообщением. Путь к `data.db` считать от корня проекта, а не от текущей папки запуска (иначе Gunicorn из другого каталога создаст пустую БД).

### Т5. Логирование ключевых операций и ошибок API
**Что значит:** по логу можно восстановить, что делал пользователь и почему упал запрос.
**Как:** `logging` с `FileHandler('logs/app.log')` + `StreamHandler`, формат с датой/временем/уровнем. Логируем: старт приложения, каждый исходящий запрос (метод, URL без токена, код ответа, длительность), ошибки с текстом, вход/выход пользователя (если будет авторизация).
**Грабли:** логировать токены и персональные данные нельзя; `print()` — не логирование; папку `logs/` создавать при старте (`os.makedirs(exist_ok=True)`), иначе первый запуск упадёт.

### Т6. Устойчивость к ошибкам API
**Что значит:** API лежит / таймаут / 500 / битый JSON → пользователь видит человеческое сообщение, приложение работает дальше.
**Как:**
- `try/except requests.Timeout`, `requests.ConnectionError`, `requests.HTTPError`, `ValueError` (битый JSON);
- свой класс `ApiError` с «человеческим» текстом;
- на уровне роутов: поймали → `flash("Нет связи с сервером СМП. Попробуйте позже.", "danger")` → рендер страницы (для списка — с тем, что есть, либо пустой);
- коды 4xx (кроме 401/403) — ошибка данных, 401/403 — «нет доступа», 5xx — «сервер недоступен».
**Грабли:** `except Exception: pass` — худшее, что можно сделать; нельзя отдавать пользователю `traceback` или сырой текст исключения; при POST-ошибке нельзя терять введённые данные (вернуть форму с заполненными полями).

### Т7. Запуск на отечественных ОС (ориентир — Debian)
**Что значит:** приложение ставится и работает на Linux, а не только на Windows-машине разработчика.
**Как:** venv + `requirements.txt`, запуск через Gunicorn, инструкция в README. Системный пакет: `python3-venv` (Debian/Ubuntu/Astra) `dnf install python3` (РЕД ОС/Альт/РОСА — отличается только имя пакета).
**Грабли:** пути с `\`, `python` вместо `python3`, отсутствие `python3-venv` на чистой Astra, SELinux/firewalld на РЕД ОС (порт 8000), запуск от root.

## 2.6. Этапы — что делать и когда считать этап закрытым

**Этап 1. Подготовка.** Репо, `.gitignore`, README, venv, пакеты, «Hello World».
*DoD:* у каждого участника `python app.py` открывает страницу.

**Этап 2. Заглушка API + своя БД + вёрстка.** `schema.sql` → `db.py` → `seed.py` → `data.db` → `mock_api.py` (порт 5001) → `api_client.py` → все экраны.

**Этап 3. Готовность к боевому API (самого API нет).** Убедиться, что ни один шаблон и ни один роут не знает про конкретные имена полей источника: всё живёт в `api_client.py`. Прогнать «переключение» на второй экземпляр заглушки с другим портом/префиксом — правкой только `.env`.
*DoD:* смена `API_BASE_URL` (например, на `http://127.0.0.1:5002`) не ломает приложение; адаптер покрывает все поля, которые ждёт вёрстка.
*Почему так:* реальную интеграцию делают другие люди; наша задача — отдать им один файл с понятными функциями и документированный контракт.

**Этап 4. Отказоустойчивость.** Логи, `try/except`, проверка обрывов.
*DoD:* Ctrl+C на моке → баннер + запись в логе, приложение живо.

*DoD:* открывается по `http://<ip>:8000` с другого устройства.

**Этап 6. Документация и репетиция.** README, схема, endpoint'ы, прогон демо.
*DoD:* демо проходит без импровизации.

## 2.7. Git-правила — в наших условиях

Из ТЗ: не коммитить `venv/`, `.env`, `logs/`; забирать свежий код; договориться о файлах.

## 2.9. Задача со звёздочкой (кэш) — как делать и чем рискуем

**Идея:** список вызовов и карточки держим в памяти с TTL, при обрыве показываем последнее с плашкой «нет связи, только чтение».

**Сервер:** `cachetools.TTLCache` (или свой dict + `time.monotonic()`), шифрование `cryptography.fernet`, ключ в переменной процесса (не в файле!), TTL 5–15 минут.
**Клиент:** `sessionStorage` + Web Crypto — опционально, только если реально нужно переживать перезагрузку вкладки.
**Обязательно:** блокировать кнопки создания в офлайне, писать в лог «данные из кэша».
**Риски:** данные у нас вымышленные, но привычку «ПДн не пишем на диск» сохраняем — если появится боевой API, требования по ПДн всё равно придётся согласовывать; Fernet не «магия» — ключ живёт в памяти процесса, при дампе памяти он доступен; не путать с «сохранением на диск» (запрещено).

## 2.10. Вопросы по контракту (решаем сами, а не у заказчика)

Поскольку API наш, «уточнять у заказчика» нечего — фиксируем решения и не меняем их без причины:

1. **Формат:** REST + JSON, префикс `/api`, коды 200/201/400/404/500.
2. **Авторизация:** в заглушке нет. Токен оставляем в `.env.example` как задел на боевой API.
3. **Пагинация:** не делаем — на демо 3–10 вызовов. Параметры `limit/offset` закладываем в API, но UI их не использует.
4. **Даты:** ISO 8601 (`YYYY-MM-DD`, `YYYY-MM-DDTHH:MM:SS`), храним в SQLite как `TEXT`.
5. **Обязательные поля:** `patients.full_name`, `calls.call_number`/`address`, `cases.call_id`, `diaries.note`, `appointments.doctor`/`appointment_at`.
6. **Портал врача:** `DOCTOR_PORTAL_URL` из `.env`; если пусто — кнопка неактивна.
7. **Время:** ставит сервер (`datetime('now')` в SQLite), планшет время не присылает.
8. **Запись к врачу:** врач и дата-время вводятся вручную; список слотов — только если появится боевой API.
9. **ПДн:** в примерах только вымышленные люди; `data.db` в `.gitignore`.

**Если боевой API всё же появится (не наша зона):** уточнить формат (REST/JSON-RPC/XML), авторизацию и срок жизни токена, пагинацию, обязательные поля, тестовый контур и VPN, правила SSO для портала врача.

## 2.12. Наш контракт API и схема SQL

### Схема БД (`schema.sql`, SQLite)

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS patients (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    full_name     TEXT NOT NULL,
    birth_date    TEXT,                 -- 'YYYY-MM-DD'
    policy_number TEXT,                 -- строка, ведущие нули сохраняем
    gender        TEXT,                 -- 'м' / 'ж'
    phone         TEXT,
    address       TEXT
);

CREATE TABLE IF NOT EXISTS calls (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    call_number TEXT NOT NULL UNIQUE,   -- номер вызова, напр. 'А-1024'
    address     TEXT NOT NULL,
    reason      TEXT,                   -- повод
    status      TEXT NOT NULL DEFAULT 'new',  -- new / in_progress / done / canceled
    patient_id  INTEGER REFERENCES patients(id),
    crew        TEXT,                   -- бригада
    created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS cases (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    call_id    INTEGER NOT NULL REFERENCES calls(id),
    diagnosis  TEXT,
    treatment  TEXT,
    result     TEXT,                    -- госпитализирован / отказ / на месте
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS diaries (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    call_id    INTEGER NOT NULL REFERENCES calls(id),
    note       TEXT NOT NULL,
    author     TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS appointments (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    patient_id     INTEGER NOT NULL REFERENCES patients(id),
    doctor         TEXT NOT NULL,
    appointment_at TEXT NOT NULL,       -- 'YYYY-MM-DDTHH:MM:SS'
    comment        TEXT,
    created_at     TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_calls_patient     ON calls(patient_id);
CREATE INDEX IF NOT EXISTS idx_cases_call        ON cases(call_id);
CREATE INDEX IF NOT EXISTS idx_diaries_call      ON diaries(call_id);
CREATE INDEX IF NOT EXISTS idx_appointments_pat  ON appointments(patient_id);
```

> `cases` и `diaries` намеренно **не** выводятся в карточке вызова из коробки — по ТЗ нужны только формы создания. Если API будет отдавать их в составе вызова, добавим блок «История» без изменения схемы.

### Эндпоинты заглушки (`mock_api.py`, порт 5001)

| Метод | URL | Тело запроса | Ответ |
|-------|-----|--------------|-------|
| GET | `/api/health` | — | `{"status":"ok"}` |
| GET | `/api/calls` | — | `{"items":[...], "total":N}` |
| GET | `/api/calls/<id>` | — | объект вызова + `patient` |
| GET | `/api/calls/<id>/cases` | — | `{"items":[...]}` |
| GET | `/api/calls/<id>/diaries` | — | `{"items":[...]}` |
| GET | `/api/patients/<id>` | — | объект пациента |
| POST | `/api/calls/<id>/cases` | JSON | `201` + созданный объект |
| POST | `/api/calls/<id>/diaries` | JSON | `201` + созданный объект |
| POST | `/api/patients/<id>/appointments` | JSON | `201` + созданный объект |

**Ошибки:** `400` — не прошла валидация, `404` — нет вызова/пациента, `500` — внутренняя ошибка (для демонстрации можно включить принудительный сбой переменной окружения). Формат ошибки единый:

